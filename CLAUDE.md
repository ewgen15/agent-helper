# Робота з агентами в цьому проєкті

Основна сесія (я) координує: ділить роботу, формулює завдання агентам і сама перевіряє результат.
Мова спілкування та текстів UI — українська.

## Хто що робить

**Haiku (`model: "haiku"`) — за замовчуванням для виконання.** Віддавай йому чітко окреслені задачі:
- прочитати й підсумувати план, README, код (короткий звіт);
- реалізувати змінну частину з ясним контрактом (UI, сервер, конфіг);
- написати або доповнити тести;
- виправити lint-конфіг, дрібні баги за вказаним місцем;
- зробити **локальний** коміт.

**Opus (`model: "opus"`) — лише за погодженням або коли користувач прямо попросив.** Якщо потрібен:
- спершу запропонуй користувачу і дочекайся згоди;
- запускай економно: короткий промпт зі стислим підсумком, без читання файлів, без інструментів, `effort: "low"`, ліміт слів у відповіді (~200). Типове призначення: план рішення, архітектурне рішення.

**Основна сесія** сама робить: дрібні правки (1–2 рядки), перевірку результатів, спілкування з користувачем, усе, що потребує рішення чи погодження.

## Як ділити роботу між агентами

- Кожному агентові — **власні файли**, які не перетинаються з іншими. У промпті прямо пиши: «You own ONLY …, do NOT touch …».
- Якщо агенти залежать один від одного (наприклад, UI і сервер), **заздалегідь опиши контракт** у промпті обох: формат повідомлень, URL, заголовки, коди відповідей.
- Незалежні агенти запускаються паралельно, у фоні (`run_in_background: true`). Залежні етапи — послідовно.
- У промпті агента завжди: що прочитати першим, що змінити, які тести додати, команди перевірки, і «report in N sentences».
- Якщо агент знайшов баг поза своїми файлами — хай **повідомить, а не виправляє**.

## Перевірка після агентів (обов'язково)

Не вірити звітам на слово. Після завершення агентів основна сесія сама запускає:
- `npm run build`
- `npm test` (tsc + `node:test`, зараз 340 тестів)
- `npx eslint .`
- за потреби — живу перевірку (наприклад, `curl` до сервера на випадковому вільному порту).

У фінальному звіті користувачу: що перевірено і чим; що **неможливо** перевірити без реальної Figma (мережа з iframe, `clientStorage`, вигляд вікна).

## Що потребує погодження користувача

- `git push`, будь-які зміни віддалених репозиторіїв.
- Широкі команди, що можуть зачепити чужі процеси (`pkill -f …`) — не використовувати; зупиняти лише власні процеси за PID.
- Зміни налаштувань Claude Code (наприклад, `claude mcp add`) — давати користувачу команду, самій не виконувати.
- Запуск Opus (див. вище).
- Зміни конфігів, згенерованих Figma, якщо це не було частиною завдання.

## Коміти

- Локальний коміт може робити Haiku: перед цим перевірити, що в коміт не потрапляють `node_modules`, `code.js`, секрети.
- Без `--no-verify`, без force-флагів, без зміни git config.
- Наприкінці повідомлення коміту — рядок:
  `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`

## Довідка по проєкту

- Плагін Figma «Copy Node ID → Claude»: `code.ts` (main), `ui.html` (UI), `manifest.json`.
- `server/index.js` — локальний MCP-сервер (stdio) + HTTP на `127.0.0.1`, порт за замовчуванням **3846** (3845 займає Figma Dev Mode MCP). У `devAllowedDomains` вказується `http://localhost:3846` (IP-адреса Figma не приймає).
- Сервер завершується, коли закривається stdin (так задумано для MCP); для ручного запуску у фоні потрібен відкритий stdin.
- Тести: `tests/` (`node:test`, випадкові порти 4100–4999, ніколи 3845/3846).
- `figma.fileKey` працює завдяки `enablePrivatePluginApi: true` (лише для приватного плагіна).
- `code.js` — збірка, у git не потрапляє; після змін у `code.ts` запускати `npm run build`.
