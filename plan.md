# Figma plugin: Copy Node ID → Claude

## Мета
Швидко клікнути на елемент у Figma і одразу отримати його Node ID (без копіювання посилання), в ідеалі — відправити його в Claude.

## Стек
- Figma Plugin API (TypeScript)
- Файли: `manifest.json`, `code.ts`, `ui.html`
- Опційно: локальний HTTP/MCP-сервер на домашньому сервері

## Етапи

### 1. Каркас плагіна
- Figma Desktop → Plugins → Development → New plugin… → шаблон «Empty / Run once» (з UI)
- Назва: `Copy Node ID`
- Налаштувати TypeScript-збірку (`npm install`, `tsc` watch)

### 2. Отримання ID
- У `code.ts` підписатись на `figma.on('selectionchange', ...)`
- Брати `figma.currentPage.selection` → `id`, `name`, `type`
- Для кількох виділених елементів повертати список
- Передавати дані в UI через `figma.ui.postMessage`

### 3. Копіювання в буфер
- UI (`ui.html`) показує ID, назву, тип
- Кнопка «Copy» + опція автокопіювання при виборі елемента
- Використати `navigator.clipboard` або fallback `document.execCommand('copy')` (в iframe плагіна)
- Формат копіювання: лише `id`, або `id + name`, або посилання з `?node-id=` (через перемикач)

### 4. Відправка в Claude
- **Варіант A (простий):** копіювати у зручному форматі й вставляти в чат / Claude Code
- **Варіант B (просунутий):**
  - Плагін робить `fetch` POST на локальний сервер (`http://localhost:PORT/selection`)
  - Сервер зберігає останній вибраний елемент
  - MCP-сервер віддає Claude інструмент `get_figma_selection`
  - У `manifest.json` додати `networkAccess.allowedDomains` для localhost
- Claude отримує ID → через Figma MCP/REST API бере дані ноди

### 5. Полірування
- Гарячі клавіші / швидкий запуск плагіна
- Індикація «Copied!»
- Підтримка кількох елементів
- Обробка порожнього виділення

## Перший крок
Створити плагін через меню Figma та підготувати проєкт із TypeScript. Далі — Етап 2 (`selectionchange`).

- Node ID у посиланні має формат `1-2`, а в API — `1:2`. Врахувати при копіюванні.

## Відкриті питання / ризики

**Неоднозначності специфікації**
- Чи захоплює плагін приховані вузли? §2.4 і §3 не кажуть, чи tier-и їх містять, а `skipInvisibleInstanceChildren` суперечить ідеї «надмножини». Без цього `include:["hidden"]` і рядок `# hidden nodes not captured` не мають сенсу.
- Формат повідомлення `selection-detail` між `code.ts` і UI не описаний. Контракт треба зафіксувати до етапу 5.
- Маркери: §2.4 пише `…+N nodes`, а приклад §5.2 містить `…+3 rows` і `…+0 nodes`. Уточнити, чи `rows` — окремий маркер груп.
- Ліміт «сумарно ≤ 400 записів» у валідації проти `maxNodes` 300 плюс записів шаблонів груп: чи рахуються `tpl` до ліміту?
- `nodeId` (§5.1) доступний лише в межах захопленої глибини 6. Що повертати для глибшого id: «not captured» чи помилку?
- Згортання (§2.4 п. 4) прибирає id внутрішніх TEXT. Редагування тексту рядка через id екземпляра — чи достатньо для сценаріїв Claude? Потрібне підтвердження автора.
- Нормалізація хвостових цифр у `n` (`Row 3` → `Row #`) може об'єднати різні за змістом рядки; чи прийнятно?

**Питання з §9 специфікації (потрібна відповідь користувача)**
- Tier B: depth 6 / 300 чи depth 4 / 150 заради швидкості плагіна.
- Розгортати дітей INSTANCE хоча б на один рівень, чи достатньо `ot` / `oi`.
- Маркер для hex без змінної чи стилю (`#1A2B3C!`).
- Підказка про новий tool у старому `get_figma_selection` порушує байт-сумісність — дозволити?
- Реєстр (етап 10): диск `~/.figma-selection/` чи лише пам'ять.

**Неперевіряємо без реальної Figma**
- Точні назви й поведінка async-API в dynamic-page: `getMainComponentAsync`, `getStyleByIdAsync`, `getVariableByIdAsync`, `getNodeByIdAsync`, `node.overrides`, `getStyledTextSegments`, `skipInvisibleInstanceChildren`.
- Реальний час `collect` із холодним кешем: ціль ≤ 50 мс на 60 вузлів, ймовірно недосяжна для 300 вузлів без прогріву. Таймбокс 150 мс може обривати обхід часто.
- Токени: `ceil(chars/4)` — це оцінка, а не токенізатор Claude. Бюджет §1 перевіряти лише за порівняльними замірами.

**Розмір і продуктивність**
- Tier B (300 вузлів, `maxTextChars` 120) може часто перевищувати 96 KB, тоді драбина робить кілька серіалізацій підряд. Логувати `buildMs` і кількість повторів.
- Затримка до результату ≈ debounce 250 мс + збірка до 150 мс. Для швидкого клацання це прийнятно, але треба перевірити.
- Кеш імен на 2000 записів може вичерпуватись у великих файлах; тоді частина імен піде через fallback hex.

**Конфлікти з наявним планом (`plan.md`)**
- Крок 6 плану: «виділення в пам'яті, життя сервера = життя MCP-процесу». §7 специфікації пропонує запис на диск. Це суперечить попередньому рішенню; вирішити до етапу 10.
- Крок 5 плану: формат `Figma nodes: 1:2 "Button" (FRAME)` для `get_design_context`. Compact dump його не замінює (це non-goal §1); треба явно зазначити, що два формати співіснують.
- Крок 1 плану: `networkAccess none`. Вже позначено в примітці плану; для етапу 6 потрібен доступ до `localhost`.
- Сервер слухає `127.0.0.1`, а маніфест і UI використовують `localhost`. На деяких системах `localhost` резолвиться в `::1`, і запит впаде. Перевірити на машині користувача.
- Порядок PR у §9 специфікації (6 пунктів) деталізовано тут до 10 етапів; відповідність збережено за файлами.

## Прийняті рішення (06.11.2026)

- **Приховані вузли:** у Compact Dump пропускаємо (`visible === false`), якщо специфікація не каже інакше.
- **Контракт `code.ts` → `ui.html`:** виділення надсилається одразу, як і зараз (`{type:'selection', …}`). Деталі йдуть окремим повідомленням `{type:'detail', ids:[…], detail:{…}}`. UI надсилає POST із виділенням, а коли приходить `detail` з тими самими `ids`, — повторний POST з полем `detail`.
- **Зберігання:** в пам'яті сервера. Реєстр на диску (етап 10, необов'язковий) відкладено.
- **Нотатка користувача:** кнопка «Написати нотатку» в UI, поле `note` (рядок ≤ 2000 символів, необов'язкове) у `POST /selection`, сервер віддає її в тексті MCP-відповіді (`Нотатка: …`). Нотатка очищується, коли змінюється виділення.

## Ідея: кнопка «Відправити детальний опис» (додано 06.11.2026)

- У UI поруч із полем нотатки (або в одному блоці з ним) — кнопка «Відправити детальний опис». Нотатка (поле вводу коментаря) вже є; кнопка відправляє разом з нею Compact Dump виділення.
- **Пропозиція (потребує погодження):** детальний опис збирати **за кліком**, а не на кожну зміну виділення. Потік: UI → `{type:'request-detail'}` → `code.ts` виконує `compactTree` з таймбоксом → `{type:'detail', ids:[…], detail:{…}}` → UI робить POST з `detail` і `note`. Так немає зайвого навантаження на Figma, великих запитів на кожен клік і користувач контролює, коли Claude отримує деталі.
- Залежить від етапів 3–6 зі специфікації (`compactTree`, збір у `code.ts`, повідомлення `detail`) і від інструмента `get_figma_selection_detail` (етап 7).
- Висоту вікна плагіна збільшити з 360 приблизно до 520 px (нотатка + кнопка).

## Рішення щодо кнопок деталей (06.11.2026, погоджено)

- Дві кнопки: **«Додати деталі»** (одразу збирає й відправляє, без коментаря) і **«Додати деталі з коментарем»** (відкриває поле коментаря й кнопку «Відправити»; після кліку збирає деталі й відправляє разом з `note`).
- Автоматичне перевідправлення нотатки (debounce) прибирається: `note` іде лише разом із деталями за кліком. Нотатка очищується при зміні виділення (поведінку потестувати й переглянути).
- Деталі збираються за кліком. Контракт: UI → `{type:'request-detail', requestId:number}`; `code.ts` → `{type:'detail', requestId, ids:string[], detail:object}` або `{type:'detail-error', requestId, message:string}`. UI робить POST `{fileKey, nodes, detail, note?}` лише якщо `ids` збігаються з поточним виділенням.
- Формат для Claude за замовчуванням — `compact-text` (дешевше й зручніше); JSON — опція.

## Історія записів і перегляд у плагіні (06.11.2026)

Рішення: замість одного перезаписуваного `latest` сервер тримає **історію останніх 10 записів** у пам'яті; плагін показує їх у розділі «Записи на сервері».

**Сервер (`server/index.js`)**
- Запис = `{id (зростаючий номер), fileKey|null, receivedAt, nodes, detail?, note?}`. Новий POST додає запис, найстаріший випадає (ємність 10).
- Той самий `fileKey` + той самий набір id вузлів **оновлює** наявний запис (деталі/нотатка додаються до нього), а не створює дубль, і запис стає найновішим.
- Порожнє виділення нових записів не створює й нічого не стирає.
- `GET /records` (потрібен `x-token`, та сама перевірка `Origin`/CORS, що й у `POST /selection`; 401 без токена): `{ok:true, capacity:10, records:[{id, fileKey, receivedAt, nodeCount, nodes:[{id,name,type}] (до 20), hasDetail, noteLength?/note, }]}`, найновіші першими. `detail` у відповідь НЕ входить.
- MCP: `get_figma_selection_detail` отримує необов'язкові `index` (0 = найновіший) і `fileKey`; новий інструмент `list_figma_selections` (короткий перелік). `get_figma_selection` без змін.

**Плагін (`ui.html`)**
- Розділ «Записи на сервері (N)» зі згортанням і кнопкою «Оновити». Дані — `GET http://localhost:3846/records` з `x-token`. Оновлюється при відкритті, після кожного успішного POST та за кнопкою; без постійного опитування.
- Рядок запису: час, файл (скорочений `fileKey` або «файл невідомий»), кількість вузлів і назва першого, позначки «деталі» / «нотатка»; клік розгортає вузли й текст нотатки.
- Працює лише коли ввімкнено «Надсилати в Claude» і є токен; помилки — у статусі.

## Розділення «поточне виділення» і «збережені записи» (06.11.2026, погоджено)

Мета: прості кліки по елементах не перезаписують важливі записи.

**Сервер**
- Два окремих сховища: `current` (одне, живе) і `records` (історія 10 записів з деталями).
- `current` оновлюється **кожним** `POST /selection` (з `detail` чи без; порожнє виділення робить його порожнім). У records він ніколи нічого не змінює й не стирає.
- Запис у `records` створюється/оновлюється **лише** коли POST містить **валідний `detail`** (тобто після «Додати деталі» / «з коментарем»). Той самий `fileKey` + той самий набір id оновлює наявний запис (нотатка завжди з найновішого POST). Прості POST без `detail` у records не потрапляють. Невалідний `detail` запису не створює.
- `get_figma_selection` (legacy) читає `current`.
- `get_figma_selection_detail` за замовчуванням (без `index`/`fileKey`) віддає **найновіший збережений запис**. Якщо `current` не збігається з цим записом (інший файл або інший набір id), першим рядком виводиться `Увага: поточне виділення (N вузлів) не збігається із записом #<id>`. Якщо збережених записів немає, а `current` непорожній: «є виділення (N вузлів), але деталі не надіслано — натисніть «Додати деталі» у плагіні»; якщо `current` порожній — «виділення порожнє»; якщо нічого не надходило — поточний текст. `index`/`fileKey` працюють лише по records.
- `GET /records` додатково повертає `current: null | {fileKey, receivedAt, empty:boolean, nodeCount, nodes:[{id,name,type}] (до 20)}`.

**Плагін (`ui.html`)**
- У розділі «Записи на сервері» зверху рядок «Поточне: …» (із `current`; «порожнє» / «ще не надходило»), нижче — збережені записи.
- Оновлення розділу: при відкритті, за «Оновити» та після успішного **POST з деталями** (прості POST виділення розділ не оновлюють).

## Поточний стан (09.11.2026)

Зроблено після 06.11.2026:

- **Згортання вікна:** UI шле `{type:'resize', collapsed}`, `code.ts` викликає `figma.ui.resize`. Розміри: 380 × 520, згорнуте — 56 px (`UI_WIDTH`, `UI_HEIGHT`, `UI_COLLAPSED_HEIGHT`). У згорнутому стані в заголовку показується короткий підсумок кількості вузлів.
- **Вкладки:** «Виділення» і «Записи (N)», де N — кількість записів зі статусом `new`. Вкладка «Записи» завантажує список `GET /records`.
- **Статус записів `new` / `done`:** новий запис і запис, оновлений новим POST, отримують `new`. Змінюються через `POST /records/<id>/status` і MCP-інструмент `mark_figma_selection_done` (`status` за замовчуванням `done`). Прості POST статус не чіпають.
- **Читання деталей:** `get_figma_selection_detail` без `index`/`fileKey` віддає найновіший запис зі статусом `new`, а якщо таких немає, найновіший узагалі. Заголовок виводу містить `· status=…`.
- **Чесний результат збереження деталей:** сервер відповідає `200` навіть при невалідному `detail`, але з `detail:{stored:false, error}`; валідний дає `detail:{stored:true, tier, nodes}`. UI має показувати цей результат, а не лише факт HTTP-відповіді (перевірити в `ui.html` після змін).
- **Валідатор `detail` (сервер):** записи шаблону групи (`tpl`) можуть не мати `id`; група всередині шаблону може не мати `items`; вкладеність до 10 рівнів; довші за 300 символів рядки обрізаються до 288 + `…(+N)` (не відхиляються); тіло POST обмежене 1 MB (`413`).
- **Ризик:** ліміт 400 записів `detail` (`DETAIL_MAX_RECORDS`) перевіряє сумарну кількість записів, у тому числі шаблонів. Плагін фізично видає до `maxNodes` ≤ 300 вузлів, але чи вистачає 400 з урахуванням `tpl` і `items` — уточнити на реальних фреймах.
- **Позначка обрізаного обходу:** якщо підрахунок вмісту інстансу обірвано за бюджетом, а точної кількості немає, плагін пише `…+? nodes (walk capped)` (`code.ts`, `compactListingRecord`). Кількість і рівні в такому разі є нижніми межами (`≥`).

**Напрямок дизайну (не реалізовано):** папка `design/` з референсами й `design/references/NOTES.md`. Цільовий стиль: пастельний фон-градієнт, білі заокруглені картки, кольорові плитки-лічильники, компактні теги-«таблетки», один синій акцент, округлий sans.
